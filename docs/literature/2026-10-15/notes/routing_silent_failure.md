# Routing under silent local failure: reactive vs predictive routing, router transfer across hardware, and switch cost (Sweep 3)

Scope labels used below:
- [HYBRID D-C] = hybrid device/edge-cloud work (local model on device + cloud model)
- [MODEL ROUTING] = pure model selection/cascades among (mostly) cloud-hosted models
- [AGENT RELIABILITY] = agent/tool-calling failure studies (no router)
- [RUNTIME/PRACTITIONER] = runtime docs, blogs, GitHub issues (not peer-reviewed)

Verdict labels relative to SEAM paper-2 claims: SUPPORTS / PREEMPTS (partly or fully already claimed) / CONTRADICTS / NEUTRAL.

## Q1. Which papers say reactive escalation fails for silent or confident errors, and in which settings (agents, tool calling, long context)?

### Takeaway
Several 2024-2026 papers say confidence or self-verification signals are weak proxies, and that agents miss "quiet" well-formed-but-wrong tool results far more often than explicit errors. That supports SEAM's premise. No paper found studies the specific case of a router missing errors caused by the runtime silently dropping context. One important correction: the literature already separates **pre-generation** routers (RouteLLM, Hybrid LLM; these are predictive about query difficulty) from **post-generation/cascade** routers (FrugalGPT, AutoMix; these are reactive). SEAM's line "existing routers decide escalation reactively" is therefore too broad as written.

### Cited Findings
**Taxonomy (frames the reactive vs predictive claim)**
- [MODEL ROUTING] Moslem & Kelleher, "Dynamic Model Routing and Cascading for Efficient LLM Inference: A Survey," TMLR 08/2026 (arXiv 2603.04445v3, 30 Aug 2026). It sorts routers by when they decide. Pre-generation routing picks a model before any output exists, using query properties only. Post-generation routing decides after a first response, using quality or confidence. Multi-stage cascades combine the two. Verdict: CONTRADICTS the blanket wording "existing routers are reactive". SEAM should use this taxonomy and narrow the claim. — [Survey](https://arxiv.org/pdf/2603.04445)
- Same survey: "previous work finds self-verification unreliable to repair the model's output". On verbalized confidence: "both verbalization techniques consistently exhibit low alignment between reported uncertainty and prediction correctness." Verdict: SUPPORTS (post-generation signals are weak). — [Survey](https://arxiv.org/pdf/2603.04445)
- Same survey, on hardware: "Serving a routing system also requires keeping multiple large models loaded in memory, awaiting possible selection." Edge or device-cloud routing appears only in passing. Small-model overconfidence, switch cost and multi-turn/agent routing are not discussed as limitations. Verdict: SUPPORTS that a gap exists. — [Survey](https://arxiv.org/pdf/2603.04445)

**Pre-generation (predictive about query difficulty) routers: these already exist**
- [MODEL ROUTING, edge as a motivation only] Ding et al., "Hybrid LLM: Cost-Efficient and Quality-Aware Query Routing," ICLR 2024 (arXiv 2404.14618). It is "a router that assigns queries to the small or large model … based on the predicted query difficulty and the desired quality level." It reports up to 40% fewer large-model calls with no quality drop. Small models are motivated by running on cheaper "(e.g., edge) devices", but there is no hardware or feasibility model. Verdict: PREEMPTS the "classify difficulty first" step. Does not preempt the feasibility-boundary or hardware-constraint steps. — [arXiv](https://arxiv.org/abs/2404.14618v1); [ICLR proceedings](https://proceedings.iclr.cc/paper_files/paper/2024/hash/b47d93c99fa22ac0b377578af0a1f63a-Abstract-Conference.html)
- [MODEL ROUTING] Ong et al., "RouteLLM: Learning to Route LLMs with Preference Data" (arXiv 2406.18665). A pre-generation router trained on preference data. Not re-read in this sweep. Verdict: PREEMPTS "pre-generation routing" as a general idea, not the hardware constraint. — [RouteLLM](https://arxiv.org/pdf/2406.18665)
- [HYBRID D-C] Zhang et al., "Hera: Learning Long-Horizon Coordination for Device–Cloud Collaborative LLM Agents," arXiv 2605.24598 (23 May 2026). It describes the field as: "Existing methods treat each request as an atomic unit, making a one-shot routing decision before inference begins". Hera instead routes at each agent step with a 500M Transformer that picks device or cloud. The objective counts only cloud calls and task return. Device memory, latency, energy and handoff cost are not modeled, even though memory limits motivate the work. Verdict: CONTRADICTS "existing routers are reactive" (Hera calls existing routers one-shot and pre-inference). PREEMPTS step-level device-cloud routing for agents. Does NOT preempt the feasibility constraint or switch cost. — [Hera](https://arxiv.org/html/2605.24598)

**Post-generation / reactive routers and their stated weaknesses**
- [MODEL ROUTING] Aggarwal et al., "AutoMix: Automatically Mixing Language Models," NeurIPS 2024 (arXiv 2310.12963v5). It escalates through "selective routing (routing to larger models when suggested by self-verification)". It concedes that "self-verification is not particularly effective for reasoning tasks and is often noisy and ill-calibrated" (said of LLMs in general, citing prior work). Limitation: "AutoMix is designed with a dialogue-related or context-grounded reasoning setup in mind for effective self-verification". Verdict: SUPPORTS. A reactive self-verifier is admitted to be noisy. Note the irony: AutoMix relies on the context being present, which is exactly what silent truncation removes. — [AutoMix](https://arxiv.org/pdf/2310.12963v5)
- [HYBRID D-C] Fang et al. (Purdue/Yonsei), "Bridging On-Device and Cloud LLMs for Collaborative Reasoning: A Unified Methodology for Local Routing and Post-Training," ICML 2026 (PMLR 306; arXiv 2509.24050). The on-device model "first attempts to generate a response locally and only invokes the cloud model" at the end. The prompt asks the model "to answer only when confident". The only resource constraint is a cloud-call budget. Device memory, feasibility, hardware and switch cost are not modeled. Verdict: SUPPORTS that current device-cloud routers are reactive and rely on self-reported confidence. Also a direct comparison point, since this is a recent top-venue device-cloud router with no hardware model. — [arXiv html](https://arxiv.org/html/2509.24050v4); [abs](https://arxiv.org/abs/2509.24050)
- [MODEL ROUTING] Wang et al., "Signed Rescue Routing: Harm-Aware Cascades for Efficient LLM Inference," arXiv 2609.07786 (Sep 2026; venue not stated). "Most routers prioritize examples on which the small model appears uncertain or likely to be wrong." It argues that uncertainty or error prediction is a flawed proxy. It names "confidently shared misconceptions" (neither model is right) as a failure mode, and notes that "the large model can overturn a correct small-model answer". The router runs after the small model answers, using features such as probabilities, margin and entropy. Verdict: SUPPORTS that confidence signals are poor proxies. Adds a nuance SEAM should price: escalation can also hurt. — [SRR](https://arxiv.org/html/2609.07786v1)
- [MODEL ROUTING] Wu et al., "Towards Fair and Comprehensive Evaluation of Routers in Collaborative LLM Systems," arXiv 2602.11877 (12 Feb 2026). The best probe-based router reaches about 68.7 AUROC in-domain and about 65.5 out-of-domain. The embedding-MLP baseline reaches about 59.5 and 55.2. So small-model correctness is only weakly predictable from internal signals. They note routing fails when both models converge on the same wrong answer. Setup: one pair only (GPT-5 with Llama-3.1-8B-Instruct), single runs. Caveat: their headline relative-improvement numbers do not obviously match their table averages. Verdict: SUPPORTS (weak discriminability). — [Fair router eval](https://arxiv.org/html/2602.11877v1)

**Agent and tool-calling silent failures (no router, but the same mechanism)**
- [AGENT RELIABILITY] Kraishan (Texas Tech), "Loud Failures, Quiet Failures: Fault Detection and Recovery in Tool-Using Language Model Agents," arXiv 2610.10062 (2026; single author). It uses the **BFCL multi-turn** split with fault injection: 24 tasks, 1,920 trials, models including Claude Haiku 4.5, DeepSeek-R1/V3 and Qwen3. Agents flagged a problem in 91.3% of loud-fault trials but only 58.8% of quiet-fault trials (well-formed, correctly typed, wrong content). The false-alarm rate on fault-free runs was 26.8%. "Quiet failures are the ones that reach the user as confident output, and they are the ones agents are worst at". "agents respond to the error channel rather than to the content of what a tool returns". "Adding a line to the prompt asking the agent to check each result did not move detection." Two fault-free runs reached the same end state only 63.3% of the time. Verdict: strongly SUPPORTS the parseability/error-channel blind spot, on the same benchmark SEAM uses (BFCL multi-turn). It differs from SEAM in that faults come from tools, not from runtime context loss. The run-to-run figure (63.3%) also warns that SEAM should report variance across repeated runs. — [Loud/Quiet](https://arxiv.org/html/2610.10062)
- [AGENT RELIABILITY] Gumaan (Passau), "Feedback That Backfires: Why Small Language Model Agents Repeat the Call They Just Watched Fail," arXiv 2608.23651 (24 Aug 2026). Tests six SLMs from 135M to 1.7B (Llama-3.2, Qwen2.5, Qwen3, SmolLM2). Putting the failed call in the transcript raises the chance of re-emitting it from 0.06 to 0.54. Clearing context was the worst remedy (about 2.6x more exact repeats). "The problem is therefore in the harness, not in the model's grasp of error messages". Verdict: SUPPORTS indirectly. Small local agents fail in ways that loud error feedback does not fix. Harness and context handling decide failure behavior. — [Feedback That Backfires](https://arxiv.org/html/2608.23651)
- [HYBRID D-C] Rainone et al. (Qualcomm AI Research), "When Cloud Agents Meet Device Agents: Lessons from Hybrid Multi-Agent Systems," arXiv 2605.30102 (28 May 2026). A cloud supervisor periodically checks an on-device executor. Verifiers miss failing runs about 5-15% of the time. "monolithic systems encounter out-of-context errors in ~20% of runs" for on-device agents. "incorrect early actions can cause irreversible side effects". Edge energy is modeled, not measured. Qwen3-4B/8B are mapped to phones and 14B/32B to laptops by estimated memory. Verdict: SUPPORTS that context exhaustion is a major device-agent failure regime, on the same model family (Qwen3-4B). Their context failures are reported as errors (loud), and the escalation is periodic supervision, not prediction. Partly PREEMPTS "periodic cloud supervision" as an alternative to SEAM's predictive design. — [arXiv](https://arxiv.org/html/2605.30102v1)

### Inferences
- The right framing for SEAM is not "routers are reactive." It is: pre-generation routers predict model capability from query text and assume execution is faithful; post-generation routers react to output signals. Neither models the runtime or hardware feasibility boundary, so neither can foresee failures caused by the runtime silently dropping context. The survey taxonomy and Hera's description of the field both make the unqualified claim attackable by reviewers.
- Loud/Quiet (BFCL multi-turn, 58.8% vs 26.8% baseline) gives an outside, same-benchmark analogue to SEAM's "≥48% well-formed but wrong, unseen by a parseability trigger." Citing it makes the claim look less idiosyncratic.
- Partly contrary evidence SEAM must address: Hera finds device entropy is higher on steps where device and cloud disagree, and probe routers reach about 65-69 AUROC. Uncertainty is not useless for ordinary capability errors. SEAM's claim of "indistinguishable at runtime" should be limited to the truncation-induced regime, where the context the model would need to notice its error is gone. A probe or uncertainty router baseline on truncated vs non-truncated runs would strengthen this.

### Gaps
- FrugalGPT (Chen et al.), MixLLM, RouterBench, RouterEval, RouterArena ([2510.00202](https://arxiv.org/html/2510.00202v1)), "When Routing Collapses" ([2602.03478](https://arxiv.org/html/2602.03478)), and LLMRouter ([2608.06867](https://arxiv.org/html/2608.06867v1)) were not re-read in this sweep. No quotes from them are given here.
- No paper found measures router accuracy specifically on outputs produced under runtime context truncation.
- Kadavath-style calibration of 4B-class models on tool calls was not specifically sourced in this sweep.

## Q2. Has hybrid device-cloud work already proposed predictive, feasibility-aware routing with a hardware constraint model?

### Takeaway
Not in the form SEAM proposes. The closest are HybridInfer (reacts to phone thermal headroom with an RL tier router; no memory or context feasibility constraint), HW-Router (server-side, hardware signals feed a latency predictor; explicitly assumes quality does not depend on hardware), and Hera and Fang et al. (device-cloud but hardware-agnostic). No paper found routes on a measured memory/context feasibility boundary.

### Cited Findings
- [HYBRID D-C: on-device/edge/cloud] Koul (independent researcher), "HybridInfer: Thermal-Aware Reinforcement-Learning Tier Routing for On-Device, Edge, and Cloud LLM Inference," arXiv 2609.30270 (14 Jul 2026). The router "uses the phone's thermal headroom and a query-complexity estimate as state" (a Q-table over bins). There is a heuristic forced offload near throttle. The paper notes that long prompts wedge the on-device runtime, but the learned router has no explicit feasibility constraint, and memory is not a signal. No switch cost or context-transfer modeling. "The study uses a single device model." It lists cross-device transfer as future work: "Evaluating across several device models would test how far the learned thresholds transfer". Verdict: closest PREEMPT on hardware-state-aware tier routing (thermal). Does NOT preempt the memory/context feasibility boundary, switch cost, or cross-hardware results, and it explicitly leaves the transfer question open, which SEAM's GPU vs CPU data answers. Credibility: a single-author preprint on one device. — [HybridInfer](https://arxiv.org/html/2609.30270)
- [MODEL ROUTING: server multi-GPU, not device] Kabir et al. (UCF), "HW-Router: Hardware-Aware Routing for Scalable Multi-LLM Serving," arXiv 2608.14575 (10 Jun 2026). Queue length, KV-cache usage and recent TTFT/TPOT feed a learned latency predictor. The only hard constraint is a latency SLO bound. "kv_cache_usage reflects memory availability that constrains batch size and throughput". "Quality predictions remain hardware-independent as response quality depends only on model capability." Tested on two H100s. The claim about other hardware types is asserted, not tested. Verdict: PREEMPTS "hardware-aware routing" as a term in cloud serving. Its explicit assumption that quality does not depend on hardware is the assumption SEAM's silent-truncation result directly refutes, which makes it a strong contrast citation. — [HW-Router](https://arxiv.org/html/2608.14575)
- [HYBRID D-C] Hera (arXiv 2605.24598) and Fang et al. (ICML 2026, arXiv 2509.24050). Both route device to cloud with no device memory or feasibility model. The only constraints are a cloud-call count or budget. Verdict: SUPPORTS that a gap exists. — [Hera](https://arxiv.org/html/2605.24598); [Fang et al.](https://arxiv.org/html/2509.24050v4)
- [HYBRID D-C] Narayan et al., "Minions: Cost-efficient Collaboration Between On-device and Cloud Language Models," ICML 2025 (arXiv 2502.15964). Local models degrade with context: "Increasing context length from <1K to >65K decreases performance by 13% on a simple extraction task". "these smaller LMs are currently better equipped to answer simple queries on shorter contexts." The design avoids sending long context to the cloud: "Minion reduces cloud costs by only 'reading' the data locally". MinionS reaches a 5.7x cost reduction while recovering 97.9% of remote-only performance with an 8B local model. Verdict: SUPPORTS that context length is the key feasibility axis for local models. PREEMPTS designing the protocol around context cost, but as task decomposition, not routing with a feasibility model. — [Minions](https://arxiv.org/html/2502.15964v1); [PMLR](https://proceedings.mlr.press/v267/narayan25a.html)

### Inferences
- The distinct, unclaimed contribution is "route on a measured (runtime x hardware x context-length) feasibility or failure-regime boundary used as a constraint, before generation." HybridInfer uses thermal state reactively. HW-Router predicts latency, not correctness, and assumes quality is hardware-independent. Hera and Fang et al. ignore hardware.
- SEAM should cite HW-Router's sentence on hardware-independent quality as the assumption it overturns. Under context-managed runtimes, the same model and query yields different correctness depending on memory pressure and configuration.

### Gaps
- The search did not surface PerLLM, EdgeShard, CE-CoLLM or similar edge-cloud scheduling papers in a way I could verify in this sweep. They may model device resources, but for latency or throughput rather than correctness. Worth checking in an adjacent sweep.

## Q3. Is there evidence that router quality comparisons change with device configuration?

### Takeaway
Almost none. Router benchmarks evaluate quality and cost, with no hardware or runtime dimension. Router rankings are known to shift with threshold, call-rate and domain. HW-Router shows latency-based routing reverses under load on fixed hardware. HybridInfer explicitly leaves cross-device transfer as future work. SEAM's result (a latency-triggered policy escalates 0% on GPU vs 100% on CPU, same device) appears to be new.

### Cited Findings
- [MODEL ROUTING] Wu et al. (arXiv 2602.11877): "router rankings can be highly sensitive to threshold choice". Small shifts within a 20-40% call-rate range reversed conclusions about one router. Aggregate metrics are "scenario-blind". Hardware and latency are not evaluated. Verdict: SUPPORTS that router comparisons are unstable even without hardware variation. NEUTRAL on hardware. — [Fair router eval](https://arxiv.org/html/2602.11877v1)
- [MODEL ROUTING, server] HW-Router (arXiv 2608.14575): under load, a smaller model's latency rises "eventually becoming slower than the much larger but idle Qwen2.5-14B". That is a ranking reversal driven by runtime load. It was not tested across hardware types (H100 vs V100 is asserted). Verdict: partial SUPPORT. Latency-based routing decisions depend on runtime conditions. — [HW-Router](https://arxiv.org/html/2608.14575)
- [HYBRID D-C] HybridInfer (arXiv 2609.30270): "The study uses a single device model." Transfer of learned thresholds across devices is named as future work. Verdict: SUPPORTS that the question is open and recognized. — [HybridInfer](https://arxiv.org/html/2609.30270)
- [HYBRID D-C] Rainone et al. (arXiv 2605.30102) map model sizes to phone vs laptop by estimated memory and model energy rather than measuring it. Verdict: SUPPORTS that device-cloud agent papers do not measure on real heterogeneous hardware. — [arXiv](https://arxiv.org/html/2605.30102v1)

### Inferences
- SEAM's GPU vs CPU placement result (the same latency-triggered policy goes from 0% to 100% escalation) is, as far as this sweep found, the first direct evidence that a fixed routing policy's behavior flips with hardware placement. It fills the gap HybridInfer names. Present it as "routing policies with latency or symptom triggers are not portable across placements," not as a claim about learned router rankings in general.

### Gaps
- No study found re-runs RouterBench, RouterEval or RouterArena rankings across hardware or runtime configurations.
- Did not verify whether any MLSys or SoCC 2025-26 paper studies routing portability across edge SKUs.

## Q4. Are there measured studies of silent failure from context truncation (Ollama/llama.cpp context handling, "lost in the middle", truncation)?

### Takeaway
The degradation of long-context use is well established (Lost in the Middle; Minions measured a 13% drop). Silent truncation in local runtimes is documented only by practitioners. One 2026 blog measures that Ollama drops the front of the prompt and returns 200 OK with no truncation flag, while llama.cpp's server returns a machine-readable 400 error. No peer-reviewed study found measures how often runtime truncation turns into well-formed wrong answers in agents. SEAM's measurement would be novel.

### Cited Findings
- [RUNTIME/PRACTITIONER] Desbiens, "Your LLM server lies to you when the context window overflows," blog, 2026-07-11. "Ollama silently drops the front of an oversized prompt and returns 200 OK". A 160,689-token prompt with num_ctx=32768 had only 16,387 tokens read (`prompt_eval_count`). There was no `truncated` field, warning or log. The model invented an answer ("remplissage"). In contrast, "llama.cpp is honest and returns a 400" (`exceed_context_size_error`). Verdict: SUPPORTS that the Ollama regime is silent and well-formed. CAUTION: this shows that behavior depends on the runtime (the llama.cpp server fails loudly here), so SEAM must name its exact runtime, version and configuration. — [Blog](https://yandesbiens.com/blog/contextpaw-silent-truncation/)
- [RUNTIME/PRACTITIONER] odysseus-dev issue #3535 (undated): "Odysseus packs past what the server holds and LM Studio silently truncates the oldest messages". Also: "LM Studio's OpenAI-compatible `/v1/models` does NOT report the loaded window". The agent harness cannot see the true loaded window, so it cannot even compute feasibility. Verdict: SUPPORTS both the silent regime and the case for SEAM measuring the boundary externally. — [GitHub issue](https://github.com/odysseus-dev/odysseus/issues/3535)
- [RUNTIME/PRACTITIONER] Other reports of Ollama num_ctx silently truncating were surfaced but not read in this sweep. — [particula.tech](https://particula.tech/blog/ollama-num-ctx-silent-prompt-truncation); [runaihome](https://runaihome.com/blog/ollama-truncating-input-prompt-num-ctx-fix-2026/); [hermes-agent issue](https://github.com/NousResearch/hermes-agent/issues/43900)
- [MODEL BEHAVIOR] Liu et al., "Lost in the Middle: How Language Models Use Long Contexts," TACL 2024 (arXiv 2307.03172). Long-context positional degradation. Not re-read in this sweep. Verdict: NEUTRAL background. It covers degradation when context is present, which is distinct from SEAM's silent removal of context. — [ACL Anthology](https://aclanthology.org/2024.tacl-1.9/); [arXiv](https://arxiv.org/abs/2307.03172v3)
- [HYBRID D-C] Minions: a 13% drop from <1K to >65K context on extraction for local models. — [Minions](https://arxiv.org/html/2502.15964v1)
- [HYBRID D-C] Rainone et al.: out-of-context errors in about 20% of monolithic on-device agent runs. Reported as errors, not silent. — [arXiv](https://arxiv.org/html/2605.30102v1)

### Inferences
- The literature shows two separate things: (1) models degrade with long context, and (2) runtimes sometimes truncate silently. No paper found connects them to routing. SEAM's contribution, measuring how often silent truncation produces well-formed wrong agent outputs that symptom-triggered routers cannot see, is unclaimed.
- Because llama.cpp's server can fail loudly while Ollama fails silently, the failure regime belongs to the runtime and its configuration, not to the model. That supports a measured constraint model indexed by runtime and hardware. It also means SEAM must avoid saying "llama.cpp silently truncates" unless it means a specific mode (for example context shift in the CLI or server). That mode was not verified in this sweep.

### Gaps
- No primary documentation was fetched for llama.cpp `--context-shift` behavior or Ollama's current default num_ctx. Verify from the official repos before stating defaults.
- "Context rot" (Chroma 2025) and arXiv 2410.18745 ("Why Does the Effective Context Length of LLMs Fall Short?") surfaced but were not read.

## Q5 (objective d). Switch or escalation cost (context re-send, KV transfer, latency) in device-cloud and routing systems

### Takeaway
Switch cost is starting to be priced in cloud-only multi-model routing: the vLLM Semantic Router SAAR prices the cached-input delta lost on a switch. Cross-model KV transfer is being explored to cut re-prefill. Device-cloud papers (Hera, Fang et al., HybridInfer, Rainone et al.) do not model handoff or context re-send cost. Minions avoids the cost by design rather than pricing it in a router.

### Cited Findings
- [MODEL ROUTING, cloud serving] Liu et al. (vLLM Semantic Router team with AMD), "Session-Aware Agentic Routing," vLLM blog, 2 Jun 2026. "SAAR therefore prices a cached-input checkout delta". "The longer and more expensive the session, the stricter the policy becomes about discarding prefix locality." "Switching away from it may require the next physical model to pay a much larger input cost". In a policy matrix of 21,600 turns, single-turn routing made 9,709 switches with 0% cost reduction. SAAR made 2,011 switches with 78.71% estimated cost reduction and a -0.0453 quality delta. No direct measurement of re-sent tokens. Verdict: PREEMPTS "price switch cost explicitly" for cloud multi-model agent routing. SEAM's distinct angle is device-to-cloud escalation, where the local KV state cannot be reused remotely and the whole context must be re-sent. — [vLLM blog](https://vllm.ai/blog/2026-06-02-session-aware-agentic-routing)
- [MODEL ROUTING, related] "MTRouter: Cost-Aware Multi-Turn LLM Routing with History–Model Joint Embeddings" (arXiv 2604.23530) and "The Workload–Router–Pool Architecture" (vLLM Semantic Router vision paper, arXiv 2603.21354) surfaced. Not read. Likely relevant to multi-turn switch cost. — [MTRouter](https://arxiv.org/html/2604.23530v1); [WRP](https://arxiv.org/html/2603.21354v2)
- [KV TRANSFER] "Cross-Model KV Cache Transfer in LLMs" (arXiv 2608.03893; authors not shown on the page read): "introduces a closed-form mapper for cross-model KV cache transfer", "cutting LLM prefill latency by up to 25× while preserving accuracy". A lemonade-sdk router issue discusses using it for same-family local escalation (issue not read). Verdict: NEUTRAL or complementary. A possible way to reduce switch cost, but for same-host same-family models, not device-to-cloud over a network. — [Emergent Mind summary](https://www.emergentmind.com/papers/2608.03893); [lemonade issue](https://github.com/lemonade-sdk/lemonade/issues/2966)
- [HYBRID D-C] Hera: "Context transfer or switch cost: Not addressed. The objective does not penalize handoffs" (summary of the paper). Fang et al.: no switching cost. HybridInfer: no switch-cost or context-transfer modeling. Rainone et al.: cost is cloud API spend plus estimated edge energy, with no separate handoff cost. Verdict: SUPPORTS a gap in device-cloud work. — [Hera](https://arxiv.org/html/2605.24598); [Fang et al.](https://arxiv.org/html/2509.24050v4); [HybridInfer](https://arxiv.org/html/2609.30270); [Rainone et al.](https://arxiv.org/html/2605.30102v1)
- [HYBRID D-C] Minions avoids cloud context cost by having the local model "read" the data locally. That is a protocol choice, not a priced routing decision. — [Minions](https://arxiv.org/html/2502.15964v1)
- [MODEL ROUTING] The routing survey notes that cascades "can still incur multiple model calls per query, introducing additional inference latency". It is not framed as context re-send. — [Survey](https://arxiv.org/pdf/2603.04445)

### Inferences
- SEAM should cite SAAR as prior art for pricing switch cost in cloud routing, and state its difference: device-to-cloud escalation in a multi-turn agent re-sends the whole accumulated context at uncached input price, plus upload latency, with no shared prefix cache. That cost grows with turn depth, which is exactly when local feasibility also fails. That joint growth is the argument for deciding early and predictively.

### Gaps
- arXiv 2610.19292 ("Whose Turn Is It? Context-Guided Model Routing for Stateful Agents") could not be read because of the fetch rate limit. It may preempt context-aware switch-cost routing for stateful agents. Must be checked manually.
- TRACE-ROUTER (arXiv 2607.22465) and "Agentic Routing: The Harness-Native Data Flywheel" (arXiv 2607.11399) surfaced but were not read. — [TRACE-ROUTER](https://www.alphaxiv.org/abs/2607.22465); [Agentic Routing](https://huggingface.co/papers/2607.11399.md)
- No measured device-to-cloud context re-send cost (tokens, dollars, latency) was found in academic work.

## Q6 (objective e). Is "routers escalate on infeasibility symptoms rather than incorrectness" already documented?

### Takeaway
Not as a named finding. Practitioner "LLM fallback" material describes escalation on timeouts, errors or outages, which is infeasibility symptoms by design. The academic "Loud/Quiet" study shows agents respond to the error channel, not to content. No paper found makes SEAM's specific point that symptom-triggered escalation catches infeasibility but misses silent incorrectness, and that its behavior flips with hardware placement.

### Cited Findings
- [AGENT RELIABILITY] Kraishan, arXiv 2610.10062: "agents respond to the error channel rather than to the content of what a tool returns". This is the closest academic statement of the same mechanism, at the agent level rather than the router level. Verdict: partial PREEMPT of the mechanism. SUPPORTS SEAM's framing. — [Loud/Quiet](https://arxiv.org/html/2610.10062)
- [RUNTIME/PRACTITIONER] Industry fallback guides frame fallback or failover as triggered by provider errors, timeouts or outages, not by answer quality (search results only, not read).

Provisioning and routing when failure is unobservable

Abstract
Hybrid execution treats a local hardware configuration as a routing target rather than a deployment: each agent step is dispatched locally or sent to a remote endpoint at monetary cost. Cloud is not another configuration knob. It does not reallocate a fixed resource within the machine; it removes the constraint for that step and replaces it with a price, which makes the feasible set elastic and the binding constraint economic rather than physical.
Existing routing systems resolve the dispatch decision by reacting to observed quality: a degraded or failed local result triggers escalation. We show that this mechanism depends on an assumption that does not hold on consumer hardware. In the paging and out-of-resources regimes a router receives a signal and can escalate. In the context-dropping regime it receives a well-formed, confident, wrong answer that is indistinguishable at runtime from a correct one, so no reactive policy can recover.
We therefore treat routing as predictive rather than reactive. The regime and feasibility boundary measured in the preceding characterization are consumed as a constraint model, and each step is dispatched by classifying difficulty, checking feasibility against that boundary, checking remaining budget, and selecting a local, remote, or cached path. Retention policy enters the same decision, since the reachable context depends on what is kept. Switch cost is priced explicitly, as escalation requires re-sending context and that cost is measurable in the orchestration overhead decomposition.
Because the regime is a property of the hardware configuration, the choice of what to provision and the choice of how to route are a single decision. Selecting unified memory purchases observable failure at a latency cost; selecting a context-managed runtime under constrained memory purchases speed and unobservable incorrectness. We report a design-space exploration over hardware configurations and routing policies, yielding a Pareto surface across task quality, cloud spend, and hardware bill of materials, and a provisioning case study translating that surface into a concrete answer for how much memory a device should carry and what routing policy keeps that configuration viable at a given monthly spend.
